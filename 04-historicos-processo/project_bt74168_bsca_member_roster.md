BT-74168 (Task, Medium priority, reported by Bri Boyer 2026-07-09, assigned to Diogenes) — `BSCA_GroupSubmissions_MemberLevel` "consistently faulting for a selector issue with navigating to the 'Member Roster'". Almost all jobs faulted the week of the ticket, 11 orders queued. Investigated 2026-07-10 via `/benops-ticket-investigation`. **Root cause found, fix proposed, not yet implemented.**

**Sheets:** ticket not found in `RPA BenOps Nov 2025` tracker — Status/Dev Start Date not auto-updated, needs manual entry.

**Root cause is NOT the reported symptom.** `Click 'Member Roster': SelectorNotFoundException` (closest matches "Member 360" 80%, "Cancel member" 73%) is a **downstream/secondary** failure of the ReFramework's exception-recovery path in `ProcessLayer/UpdateEmployeeDetails.xaml`, not a broken selector per se. Confirmed via full robot-log sequences (not just the Info/error summary) on 2 separate Production faulted jobs (2026-07-08 `6d39d36f-...`, 2026-07-09 `bc6981cc-...`):

1. A primary activity fails first — 3 different observed triggers across the 2 jobs: `Click 'Edit Subscriber'` → `"outside of screen bounds"` (`UpdateEmployeeMedicalBenefits.xaml`), `Click 'Edit Subscriber'` → `"verification failed, action did not have the expected outcome"` (same file), `Click 'Add dependent'` → selector not found (`AddDependent.xaml`/`UpdateEmployeeDependents.xaml`).
2. Recovery path in `UpdateEmployeeDetails.xaml` kicks in: `Click_7` "Click 'Go back to group'" (line 742) fires, logs `"Clicked on Go back to group (2)"`, **no exception thrown**.
3. ~30-40s later `Click_8` "Click 'Member Roster'" (line 765) times out → `SelectorNotFoundException` — this is what the ticket/reporter actually sees and reported.
4. This 2-step failure recurred on **3/3 transactions in each of the 2 inspected jobs**, regardless of the step-1 trigger — hits ReFramework's "3 consecutive System Errors" threshold → job Faulted.

**Code-level cause of steps 2-3:** `Click_7` (`UpdateEmployeeDetails.xaml:742`) and its sibling fallback `Click_5` (line 667) both use `SendWindowMessages="True"` — the exact legacy interaction mode already proven unreliable on this Salesforce LWC/OmniStudio portal for `Click 'Edit Subscriber'` (per [[project_bt73708_bsca_group_member_level]]: "SendWindowMessages... mandava a mensagem pra coordenada errada, falhava silenciosamente, form nunca abria"). Every OTHER click on these same two elements in this file (`Click_1`, `Click_6`, `Click_8`) already uses `SimulateClick="True"` successfully. When `Click_7`/`Click_5` silently no-op, the page never navigates back to the group view, so the following `Click 'Member Roster'` genuinely can't find the tab and times out (~30s default selector timeout matches the observed gap exactly).

**Important cross-reference:** BT-73708/PR #2883 (merged 2026-07-02 into `develop`, **live in Production as v6.2.9** — confirmed via `uip or processes list`, `FolderKey da841a0f...`/`Benefits` root, `IsLatestVersion: true`) already fixed ONE `Edit Subscriber` failure mode (JS `scrollIntoView` before the `HardwareEvents` click in `UpdateEmployeeMedicalBenefits.xaml`). But even with that fix deployed and running for a week, `Click 'Edit Subscriber'` STILL intermittently fails (2 different error signatures seen: bounds + verify-failed) — the scrollIntoView fix is NOT fully sufficient, though this ticket's fix doesn't need to solve that to close the loop (see Fix section — fixing the recovery path prevents the job-level fault even if the primary click still occasionally fails). [[project_bt73708_bsca_group_member_level]]'s own pending list already flagged "Member Roster ainda não resolvido, não fazia parte deste PR" — confirms this was a known-but-deferred gap, not a new regression.

**3 prior fix attempts already made on `Click 'Edit Subscriber'` alone** (BT-73415/#2792, #2798, BT-73708/#2883) — SendWindowMessages → HardwareEvents → HardwareEvents+scrollIntoView — each failed to fully resolve it. Do NOT propose a 4th variant of the same click without live debug data (screen resolution / multi-monitor setup on the runtime robot vs. design-time capture, where `DesignTimeRectangle` shows x=4401/2835 — suggests a large multi-monitor virtual desktop at capture time that may not match runtime).

**Fix proposed (not implemented yet), scoped to `UpdateEmployeeDetails.xaml` only, no Library touched:**
- `Click_7` (line 742) and `Click_5` (line 667): remove `SendWindowMessages="True"`, set `SimulateClick="True"` — matches the interaction mode already working for the other 3 clicks on these same two elements in this file.
- `Click_8` (line 765) and `Click_6` (line 690): wrap in a short `ui:RetryScope` (~3x/5s) — defensive hardening, same pattern already used across BT-74147/BT-73708 work for this exact class of post-navigation flakiness.

**Risk:** low blast radius — `Click_5`/`Click_7`/`Click_6`/`Click_8` only fire on the exception-recovery branches (`currentlyInAnEE`/`disregard`), not the happy path (`Click_1`). `SimulateClick` on this exact portal's LWC buttons isn't a new/unproven mode here — sibling clicks on the identical elements already use it successfully.

**Test plan (not yet run):** 3+ Staging transactions that force the recovery path (e.g. reproduce a known-flaky Edit Subscriber/Add Dependent case), document transaction IDs, confirm no Library file touched.
