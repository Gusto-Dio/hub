BT-74147 (Task, Medium priority, reported by Bri Boyer, assigned to Diogenes) — `BCBS_TX_GroupSubmissions_NewPlan` bot "getting stuck on dependent page when adding EEs... enters deps info but isn't continuing after that." 3 failures WTD as of 2026-07-08. Investigated 2026-07-09 following `/benops-ticket-investigation`. Root cause found and fix proposed; **not yet implemented**.

**Root cause:** NOT the same bug class as [[project_bt74133_bcbs_ma_add_dependent]] (that was a missing navigation click). Here the error is `"The UiElement is no longer valid"` — a stale-element race condition. Confirmed via full (not just Error-level) Orchestrator logs on 3/3 recent failures, hitting **two different clicks** in `Processes/Benefits/CarrierAutomations/GroupSubmission/BCBS_TX/BCBS_TX_GroupSubmissions_NewPlan/ProcessLayer/EnrollEmployee.xaml`:
- `Click_28` "Add Dependent" (line 815) — inside the dependents `ForEach`, fires right after entering the loop.
- `Click_30` "Continue" (line 1209) — fires immediately after the dependents `ForEach` ends, right after the last dependent's `Click 'Save'` (`Click_29`, line 1174).

Neither activity caches an `Element` handle (`Element="{x:Null}"`) — the race is against the portal's AJAX re-render after `Click 'Save'`, not classic UiPath element-caching reuse. `EnrollEmployee.xaml` hasn't changed since the Windows migration (#2596) — not a code regression. Checked older Failed items (07-02, 07-03) — completely different, unrelated errors (auth token, navigation selector) — confirms this exact "UiElement is no longer valid" signature is new/isolated to the week of the ticket, consistent with an external portal-side timing change rather than a code regression.

**Why it "looks stuck" to the business:** after each failure the framework logs `Process sleeping for 5 minutes` (Warn level) before retrying. One transaction observed: Started 11:01:53 → fails at `Click 'Add Dependent'` 11:03:38 → sleep 5min → retry Started 11:09:33 → fails at `Click 'Continue'` 11:11:12 → sleep 5min → retry 11:17:03 → hits the (unrelated, correct) duplicate-prevention guard added in #2803/BT-73633 ("Portal application already started on a previous attempt") and gives up. ~16 minutes total of apparent no-progress on the Carrier_Order — matches the "stuck" perception exactly, even though the bot is actively retrying/failing/sleeping, not literally hung on one line.

**Fix proposed (not implemented yet):** wrap `Click_28` and `Click_30` (and `Click_29` 'Save' as precaution) in `ui:RetryScope` (NumberOfRetries=3, RetryInterval=00:00:02) — mirrors the exact pattern already used in this same file (`RetryScope_1`, line 638, for a `SelectItem` with the same class of transient post-AJAX flakiness). No new activity type, no Library touched.

**3 WF4 structural errors hit and fixed during this pass** — the "one action per line, insert after closing tag" approach breaks when the target activity is the SOLE child of a single-child container (`If.Then`, `If.Else`, or an `ActivityAction` body inside `RetryScope`/`ForEach`/etc.) that wasn't already wrapped in a `Sequence`. Each surfaced as a distinct `validate` error pinpointing the exact line (`'Then' property has already been set on 'If'`, `'Handler' property has already been set on 'ActivityAction'`) — fixed by wrapping the original activity + its new LogMessage in an explicit `<Sequence>`:
1. `SelectItem_10` ("Heath Coverage") — sole child of `RetryScope_1`'s `ActivityAction`
2. `Click_28` ("Add Dependent") — sole child of the `RetryScope_BT74147_1` I added earlier this session
3. `TypeInto_13` and `TypeInto_14` (both "PCP Number", two separate `If.Then` branches — one for the primary employee, one for dependents)

**Lesson for next time doing this kind of bulk insertion:** before blindly inserting a sibling after any activity's closing tag, check whether its immediate parent is a single-child WF4 property (`.Then`/`.Else`/`.Try`/`.Finally`/bare `ActivityAction`) without an existing `<Sequence>` wrapper — if so, wrap first. The `validate --file-path` loop catches every instance reliably (one error at a time, exact line number), so iterating on it is a safe way to converge even without perfectly predicting every case upfront.
