BT-75847 (High, reporter/assignee Diogenes) is a re-open of [[project_bt75006_oxford_newplan_zipcode_sfdc]]/BT-75454 for `UHC_SAMx_GroupSubmissions_NewPlan` (`Processes/Benefits/CarrierAutomations/GroupSubmission/UnitedHealthcare/SamX/UHC_GroupSubmission_NewPlan_SAMx`). Oxford NP orders haven't processed successfully in weeks; SFDC Carrier Order status also isn't flipping to Failed on fault.

**Root cause 1 — zip code fix from PR #3300 never actually shipped.** In `EnterCompanyInfo.xaml`, PR #3300 commented out the *wrong* activity: the old buggy blind-double-Enter `ui:TypeInto` (line ~370) was left live/uncommented, while the new verified `uix:NTypeInto` (type digits, then `NKeyboardShortcuts` Down+Enter) was the one wrapped in `CommentOut`. So production kept running the old bug with an extra Down+Enter tacked on top — desyncs the browser window scope (`SamxOne SSO` → title picks up `BnEUserToken=`) whenever the zip autocomplete has ambiguous/multiple matches, breaking the next selector (`Total Eligible Employees`). Confirmed via Orchestrator Production logs (jobs 2026-09-10/09-11, folder `CarrierAutomation`, id 944168) — exact same failure signature repeats across every recent Faulted job.

**Root cause 2 — SFDC status not updating.** In `ProcessTransaction.xaml` catch block (~line 2550), the `UpdateCarrierOrder(Failed)` call was gated on `exception.GetType.Name="BusinessRuleException"`. Real production faults (selector timeouts, `CarrierPortalException` "Login page not available") are not `BusinessRuleException`, so the gate never opened and SFDC never got the Failed status.

**Fixes applied and committed** (commit `d00afdd3442` on branch `BT-75847-uhc-samx-newplan-zip-sfdc-status`, pushed to origin).
1. `EnterCompanyInfo.xaml` — wrapped old blind-double-Enter `TypeInto` in `CommentOut` (`CommentOut_ZipOldTypeInto`), un-commented the `NTypeInto` so it's live again.
2. `ProcessTransaction.xaml` — removed the `exception.GetType.Name="BusinessRuleException"` clause from the `If_21` condition; SFDC update now fires on any non-debug failure except the two existing carve-outs ("Order is no longer in Automation Queue", "Warning in enrollment page").
3. `project.json` — `projectVersion` bumped 1.56.11 → 1.56.12 (1.56.11 already sat unactivated in the Production feed from an unrelated earlier publish — same "Package already exists" trap as PR #3301 on the prior BT-75454 fix, avoided proactively this time) and `Gusto_Benefits` floor aligned to 1.559.34 per root `dependencylock.json`.

**2026-09-18 update — Ahsen's PR #3348 review comment: revert fix #2, keep fix #1.** Ahsen flagged that dropping the `exception.GetType.Name="BusinessRuleException"` check in `If_21` is wrong: the type-gate is intentional so a transient/technical exception gets a retry window before the bot burns the `Carrier_Order__c` Owner/status (same mechanism as [[feedback_salesforce_owner_burn_guard]] — once Owner flips to the manual-review queue, the record is effectively out of automation and can't self-heal on retry).

Verified by pulling the pre-PR blob (`git show d00afdd3442~1:.../ProcessTransaction.xaml`) — exact original `If_21` condition:
```
[NOT debugMode AndAlso exception.GetType.Name="BusinessRuleException" AndAlso NOT (automationMessage.ToString.Contains("Order is no longer in Automation Queue")) AndAlso exception.Message<>"Warning in enrollment page"]
```
My widened version (commit `d00afdd3442`, to revert):
```
[NOT debugMode AndAlso NOT (automationMessage.ToString.Contains("Order is no longer in Automation Queue")) AndAlso exception.Message<>"Warning in enrollment page"]
```

Investigated whether there's a smarter middle ground (e.g. gate on `in_RetryNumber >= MaxRetryNumber` — last-attempt-only — instead of a blanket revert): confirmed `in_RetryNumber` and `in_Config("MaxRetryNumber")` (=1 for this queue) both exist and are already threaded into `ProcessTransaction.xaml`, but today they're only used for a log field (`wbRetriesLeft`), never in the `If_21` gate. That would be the correct fix for the *original* ticket complaint (stuck-forever SFDC status on non-business faults) without reopening the burn-guard risk — but Ahsen only asked for a straight revert, and building that logic now would be scope creep beyond her ask. Decision: do the straight revert she requested; the zip-code fix (fix #1, `EnterCompanyInfo.xaml`) is what actually resolves the "faulting for weeks" complaint by stopping the fault from happening at all — the SFDC-gate widening was solving the wrong end of the problem. Log the last-retry-aware gate as a follow-up idea, not part of this PR.

**How to apply:** revert `If_21`'s condition in `ProcessTransaction.xaml` to the original text above (add back the `exception.GetType.Name="BusinessRuleException" AndAlso` clause), leave fix #1 and the version/dependency bump as-is, push, and let Ahsen re-review. Do not widen this gate again in this or sibling carrier processes without an explicit last-retry check — see new [[feedback_businessruleexception_gate_is_intentional]].
