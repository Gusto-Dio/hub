## Root cause 1 — Ownership false positive — FIXED ✅
File: `Framework/PreProcessing/CheckDataEligibility.xaml`, "Check for sum of ownership percentages" (~line 650-708).
- Was: `ownershipPercentageSum` as `x:Int32`, summed via `ownershipPercentageSum + CInt(owner("percentage"))` — rounds each term before summing, so valid splits like 36.4+36.4+27.2=100 landed on 99 after per-term rounding.
- Confirmed with 2 REAL production failures pulled from Orchestrator queue (not the ticket's literal GUIDs, which weren't findable in queue history — see below): **Nyquis Inc** (owners 36.4/36.4/27.2, queue item Id `2494339046`) and **C5R CORP.** (owners 31.64/28.36/18.18/12.36/9.46, queue item Id `2480207364`, ticket said 28.26 — minor transcription typo by Bri, same record).
- **Fix applied**: variable → `x:Double`, sum via `CDbl(owner("percentage"))`, condition → `Math.Abs(ownershipPercentageSum - 100) > 0.01` instead of `<> 100`. Mesa-tested both real cases: sum lands within ~1e-13 of 100 (float noise, well under tolerance) → no longer throws. Genuine mismatches (e.g. real sum of 95) still correctly throw since `Math.Abs(95-100)=5 > 0.01`.

## Root cause 2 — Failures don't sync to SFDC, orders age in queue — FIXED ✅
File: `Framework/Process.xaml`, outer `TryCatch_1` ("Try processing", ~line 246-1128).
- **Correction to earlier analysis in this memory**: a generic `Catch x:TypeArguments="s:Exception"` ("Handle System Exception") DOES exist (line 981) — it is NOT missing, contrary to what this memory said before. It even calls `UpdateCarrierOrder.xaml`.
- **Real bug**: that call is gated by an `If` (line 1024) requiring `exception.GetType.Name="BusinessRuleException"` — a condition that structurally can never be true inside this catch, because WF's `TryCatch` always routes a real `ui:BusinessRuleException` to the sibling, more specific `Catch x:TypeArguments="ui:BusinessRuleException"` (line 800) first. So for genuine system exceptions the `If.Then` (which calls `UpdateCarrierOrder` with `Failed`) never runs — confirmed by comparing byte-for-byte against the BRE catch's "Handle BRE" block (line 800-928), which has the identical condition text but is tautologically-true there (its `exception` is typed `ui:BusinessRuleException`). Classic copy-paste-without-adapting-the-guard bug.
- **Log evidence, fully cross-referenced** (job `5fa0850d-6b30-4cfa-abdd-5302de9ac157`, 2026-07-19, Faulted): 4x pattern of `Error` level `NavigateToQuote.xaml` selector failure (`<html app='chrome.exe' title='Home'/>` not found, closest matches `title='CreateQuote'` 63%, `title='Producer Toolbox'` 60%) immediately followed (~0.3-0.4s later) by `Warn` level `System exception. Retry: N. The activity 'Try Catch' with ID 38 threw or propagated an exception while being canceled.` — this is the exact message class Bri quoted in the ticket ("ID 40" vs log's "ID 38" — just a build/version ID difference, same failure). Job ultimately faults with "Failed to initialize after 3 attempts". Same generic-catch dead-condition bug also affects other unrelated selector failures seen in later job runs (`GroupDetails.xaml` 07-22, `QuotingLicenseAndContractValidation.xaml` / `ChooseSignatureFormat.xaml` 07-23) — fix covers all of them, not just `NavigateToQuote`.
- **Fix applied**: removed `exception.GetType.Name="BusinessRuleException" AndAlso ` from the `If` condition at line 1024, keeping only the two `NOT(...Contains(...))` guards against "Order is no longer in Automation Queue"/"...Ready for Submission Prep stage" messages (those still work fine, they're evaluated against `automationMessage` which is independent of the exception-type check).
- Did NOT touch `NavigateToQuote.xaml`'s hardcoded `title='Home'` selector itself (task #2, still open) — the SFDC-sync fix is independent of whether the selector itself ever gets hardened; it just makes sure that WHEN it fails, SFDC finds out.
